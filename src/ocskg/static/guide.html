01 / BACKGROUND背景与项目目标

企业正在把 LLM、RAG 和 Agent 放进真实业务流程里。问题不只是“模型会不会说错”，而是它是否会越权读数据、执行危险动作、泄露敏感信息，或者被恶意上下文劫持。

传统安全底座

原有 SentinelGraph 已经能做事件归一、图关联、规则检测、历史复盘和文本补图。

新增产品边界

现在要把这些能力升级成 AI Security 控制面，供企业 AI 应用直接接入。

面向客户交付

不是给内部代码加补丁，而是提供网关、控制台、策略、审批和审计能力。

开源参考实现

适合 POC、客户演示和平台原型。生产部署仍需补足租户隔离、RBAC、审计与治理。

02 / ARCHITECTURE从 AI 请求到可审计结论

产品层把 AI 流量拆成四个控制点：输入、上下文、工具、输出。事实底座仍然由 OCSF、StarRocks、图边与审计表承担，LLM 只消费被允许的上下文。

INPUTPrompt / Query

检测注入、越狱、编码绕过和敏感信息。

CONTEXTRAG

按租户与角色过滤文档，拦截间接注入。

TOOLSAgent Actions

写操作、外联和执行命令进入审批流。

OUTPUTModel Response

对密钥、密码和 PII 做脱敏与阻断。

AUDITEvidence Trail

保留原始输入、决策、复核和处置记录。

关键原则：先做策略，再做推理。任何结果都应能回溯到输入、上下文、工具调用和审核动作。

03 / FUNDAMENTALSOCSF 仍然是事实层

OCSF 负责统一安全事件语义，StarRocks 负责存储和关联，图谱负责证据展开。AI Security 不是替代这层，而是在其上增加面向企业 AI 的治理边界。

层职责产品输出
事实层事件、日志、文档、图边、告警、审计可追溯证据
控制层Prompt、RAG、Agent、输出、审批allow / review / block
治理层策略、角色、租户、保留、复核控制台与报表

04 / OLAP + LAKEHOUSE为什么仍然选 StarRocks？

因为它既能承载事件事实，也能承载安全控制面所需要的审计、文档和向量数据。对客户来说，这意味着一套统一的数据与治理底座，而不是多个割裂系统。

热数据

实时事件、风险发现、审批和审计。

上下文数据

RAG 文档、策略、知识库与模型输出。

控制数据

规则、允许列表、角色映射和风险标签。

归档数据

历史复核、审计导出和合规报告。

05 / GRAPH + DETECTION图关联、规则和告警

原来的攻击图和检测规则仍然保留，但它们现在也服务于 AI 安全。比如，恶意文档、异常工具调用和输出泄露都可以落到统一的告警和审计流里。

重要区分：相关性不等于归因

一个请求命中了注入、越权或泄露规则，只说明它需要拦截或复核，不代表模型、用户或文档已经构成最终事故归因。

06 / RETROSPECTIVE历史行为聚类与事后复盘

历史复盘能力可以用来查看某个 AI 应用在一段时间内是否持续命中护栏、是否频繁触发审批、是否存在高风险输出模式。它更像治理分析，不是实时阻断。

07 / VECTOR + GRAPHRAGRAG 在产品里的位置

RAG 不只是“把文档塞给模型”，而是把可检索内容做权限、可信度和来源控制。产品层必须明确：哪些文档可被当前身份检索，哪些上下文需要隔离，哪些结果只能给人工复核。

  • 向量相似度用于找相关文本，不是放行依据。
  • 检索上下文必须带来源、角色和可信度标签。
  • 无权限的文档应被隔离，而不是悄悄拼进 prompt。

08 / TEXT-TO-GRAPH文本补图仍然有用

安全报告、工单和威胁情报仍然是证据源。它们可以继续补图、补 IOC、补审核记录，也可以作为 AI Security 的输入上下文被审查。文本关系默认保持 pending_review，只有追加人工审核记录后才进入可采信证据链。

09 / AI SECURITY PRODUCT LAYER怎么把这些功能作为产品提供给用户？

AI Gateway

用户把自己的 AI App 接到网关，网关负责实时检查、脱敏、放行或阻断。

RAG Guardrails

文档检索前做权限过滤，检索后做间接注入和上下文污染检测。

Agent Guardrails

工具调用前做审批，危险动作进入 human-in-the-loop 流程。

Audit & Compliance

完整记录输入、上下文、工具参数、输出、审核和最终处置。

10 / PRODUCT SHAPE产品形态

这不是一个单一 API，而是一套可供企业采购和接入的产品组合。

  • 在线防护：接在 LLM / RAG / Agent 前。
  • 离线扫描：扫知识库、提示词库、工具配置和模型输出历史。
  • 治理控制台：看策略、告警、审批和审计。
  • 开放 API：让工程团队嵌入自己的平台或网关。

12 / INTEGRATION第三方 REST API

所有第三方接口以 /v1 为前缀。现在除了原有的事件、图谱、检测和文本补图接口，还新增了 /v1/ai-security/assessments，用于评估客户自己的 AI 请求流。生产环境应设置 INTEGRATION_API_KEYS，并要求调用方在请求头携带 X-API-Key。

# AI Security 控制面 curl -X POST http://localhost:8000/v1/ai-security/assessments \\ -H 'content-type: application/json' \\ -d '{ "tenant_id": "demo", "app_id": "support-agent", "user_role": "support", "mode": "mock" }' # 原有入口仍然保留：/v1/events、/v1/graph/{entity_id}、 # /v1/agent/investigations、/v1/text-graph/extract

13 / PRODUCTION生产安全边界与下一步

  • 在入口层实施 OIDC/mTLS、租户映射、速率限制和审计。
  • 把客户 AI 请求和敏感上下文当成受管制数据。
  • 对 PII、密钥和模型输出做脱敏、保留和访问控制。
  • 把审批结果接入工单、SOAR 或人工复核流。
从 POC 进入产品化的建议顺序：先做控制台和评估 API，再接网关和审批流，最后把策略沉淀成企业治理模板。
